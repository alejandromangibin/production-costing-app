## In short (for Al)

- **Stock ledger.** Every change to an ingredient's stock is written once, as a line in a stock ledger,
  and is never changed or deleted (D-23). The one exception is the owner correcting a purchase's supplier,
  reference or expiry date (INV-17); the old values are kept.
- **Current figures.** Each ingredient keeps its current on hand and average as a copy of the ledger, for
  fast screens and safe saves. A check recomputes the copy from the ledger and must always agree. It runs
  in the tests, after every restore, and on demand.
- **Exact numbers.** Quantities are stored in thousandths of the base unit (2.5 mL is stored as 2500). The
  average is stored in ten-thousandths of a centavo. Nothing is stored as a decimal that can drift.
- **Two people at once.** When two people save at the same time, the second waits for the first,
  ingredient by ingredient. A run whose prices changed after review is refused and must be reviewed again.
  The check reveals no costs to staff. In the same way, a run is refused if someone else's save meanwhile
  pushed an ingredient below zero, so nobody saves past a warning they were never shown. This refusal is new;
  the BRD did not ask for it.
- **Business separation.** The new tables are kept inside each business like the existing ones: a business
  stamp on every row, the database wall, and same-business links. The app can add ledger lines but cannot
  change or delete them.
- **Three database changes.**
  - 005 (part 4a): settings, ingredients, the ledger and the purchase-correction history.
  - 006 (part 4b): ingredient details on run cost lines.
  - 007 (part 4c): recipes, only sketched here.

## 1. Tables (database change 005, part 4a)

### 1.0 Common rules for every new table

Every new table copies `002_multitenant.sql` and `004_price_history.sql` exactly:
- `id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. "By default" lets restore insert the original ids.
- `tenant_id integer NOT NULL DEFAULT NULLIF(current_setting('app.tenant_id', true), '')::int REFERENCES tenants (id)`.
- `UNIQUE (tenant_id, id)`, and a composite `(tenant_id, x_id)` foreign key for every link.
- `ENABLE ROW LEVEL SECURITY`, not forced (D-22: forcing it blocks backup and admin reads, which run as the
  table owner). Each table gets the same `tenant_isolation` policy, `USING` and `WITH CHECK`.
- Grants are written out per table below. **Each new sequence gets its own `GRANT USAGE, SELECT ... TO costing_app`**:
  - 005: `business_settings_id_seq`, `ingredients_id_seq`, `stock_movements_id_seq`, `purchase_detail_changes_id_seq`.
  - 007: its own sequences.

  The blanket grant in 002 only covered the sequences that existed then. Inserts into an identity column work
  without this grant, because PostgreSQL does not check sequence permissions for them. It is kept so the new
  tables match the existing ones and a direct `nextval` behaves the same; the catalog test pins it.
- Who-fields (D-25): `*_by_user_id integer NOT NULL` and `*_by_name text NOT NULL CHECK (*_by_name <> '')`, plus a
  `timestamptz NOT NULL DEFAULT now()`.

### 1.1 `business_settings`: at most one row per business

| Column | Type | Notes |
|---|---|---|
| id | identity | as 1.0. Having an `id` keeps backup and restore unchanged, since they sort and renumber by `id` |
| tenant_id | | `UNIQUE (tenant_id)` |
| inventory_live_since | date, null | Cutover day. Null means inventory is not live yet. What it controls: section 6 and D-34 |
| live_set_by_user_id, live_set_by_name, live_set_at | null until set | who set it and when. CHECK: these and `inventory_live_since` are all null or all set |

- **Reading:** a plain `SELECT`, with no lock and no insert. A missing row means "not live". This covers
  staff GETs, the run preview (also allowed while a subscription has lapsed), and purchases.
- **Saving a run:** it first runs `INSERT ... ON CONFLICT (tenant_id) DO NOTHING` (Save writes anyway), then
  `SELECT ... FOR SHARE` on the row, **before any ingredient lock** (section 4, rule 0). Because the row then
  always exists, even the first switch to live cannot overlap a Save, and no run is saved under the old rules
  while the owner is switching inventory live.
- **Setting the live date:** the only writer. It runs `INSERT ... ON CONFLICT (tenant_id) DO NOTHING`, then
  `SELECT ... FOR UPDATE`, then the UPDATE.
- **The owner sets it once, to today** (in the business's time zone, never a past or future date). The server
  refuses to change or clear it afterwards. A past date would leave runs that were already saved after it
  with peso lines and no stock use.
- **Grants:** SELECT, INSERT, UPDATE.
- **No expiry window column** (dropped after review). The ingredient expiry board keeps its warning window
  in the browser, exactly like the batch board (`web/src/pages/Expiry.tsx`), because INV-15 says "like the
  batch expiry board".

### 1.3 `stock_movements`: the ledger (append-only)

It holds facts only. Running totals are never stored on ledger rows, because a back-dated entry changes them

| Column | Type | Notes |
|---|---|---|
| ingredient_id | integer NOT NULL | FK (tenant_id, ingredient_id) to ingredients |
| kind | text NOT NULL | 1.4 |
| effective_date | date NOT NULL | the day it happened. Back-dating has no limit (Q45); future dates: Q54 |
| quantity_milli | bigint NOT NULL CHECK between -10^10 and 10^10 | **signed** change, in thousandths of the base unit |
| total_cost_cents | integer null CHECK 0 to 2,000,000,000 | 1.4 |
| supplier, reference | text NOT NULL DEFAULT '', max 120 | purchases only (1.4). Correctable (INV-17) |
| expiry_date | date null | purchases only (1.4). Correctable (INV-17) |
| reason | text NOT NULL DEFAULT '', max 300 | 1.4 |
| run_id | integer null | FK (tenant_id, run_id) to runs |
| run_cost_id | integer null | FK (tenant_id, run_id, run_cost_id) to run_costs (tenant_id, run_id, id). 005 adds that unique key to run_costs. 006 adds the ingredient match (3.2) |
| unit_cost_e4 | bigint null CHECK 0 to 10^12 | the average a run line used (BR-20) |
| reverses_movement_id | integer null | FK (tenant_id, ingredient_id, reverses_movement_id) to stock_movements (tenant_id, ingredient_id, id), which needs `UNIQUE (tenant_id, ingredient_id, id)`. So a reversal can only point at a line of the **same ingredient** in the same business |
| entered_by_user_id, entered_by_name, entered_at | | 1.0 |

**Indexes:**
- `(ingredient_id, effective_date, id)` for the replay, and `(run_id)`.
- Unique: `(reverses_movement_id)`, so a line is reversed at most once.
- **One opening balance per ingredient (Q39, Q46, Q51 yes).** A wrong opening can be reversed and entered
  again, so there is no unique index on openings: it would still count the reversed opening and refuse the new
  one. Instead, the server allows at most one *standing* opening balance (one that is not reversed), checked
  under the ingredient lock. The stock check (2.4) reports any ingredient with more than one.
- Unique: `(run_cost_id) WHERE kind = 'run_use'`, and the same `WHERE kind = 'void_return'`. These guard in the
  database against using or returning one run line twice.
- `supplier`, `reference` and `expiry_date` are in no unique index, so correcting them never conflicts with
  foreign-key locks.

**Grants:**
- SELECT and INSERT.
- UPDATE on the columns `supplier`, `reference` and `expiry_date` only, as a column-level grant.
- No DELETE.

The CHECKs in 1.4 limit those three columns to purchases, so even a correction cannot put an expiry date on
another kind of line.

### 1.4 Kinds of stock movement and their CHECK constraints

`CHECK (kind IN ('opening', 'purchase', 'purchase_reversal', 'run_use', 'void_return', 'spillage', 'spoilage', 'count_correction'))`.

| kind | quantity_milli | total_cost_cents | supplier, reference, expiry | reason | run_id, run_cost_id | unit_cost_e4 | reverses_movement_id | Who |
|---|---|---|---|---|---|---|---|---|
| opening | > 0 | set | empty or null | **required** (INV-08; the screen fills in "Opening balance") | null | null | null | owner |
| purchase | > 0 | set | allowed | optional | null | null | null | owner, staff |
| purchase_reversal | < 0 | null | empty or null | **required** | null | null | **set** | owner |
| run_use | <= 0 (a 0 line is allowed, INV-06) | null | empty or null | optional | **set** | **set** | null | owner, staff (saving a run) |
| void_return | >= 0 | null | empty or null | optional | **set** | null | null | owner (voiding a run) |
| spillage, spoilage | < 0 | null | empty or null | **required** | null | null | null | owner |
| count_correction | <> 0 | null | empty or null | **required** | null | null | null | owner |

Each column is written as one CHECK that ties it to the kinds. For example:
- `(total_cost_cents IS NOT NULL) = (kind IN ('opening', 'purchase'))`
- `kind = 'purchase' OR (supplier = '' AND reference = '' AND expiry_date IS NULL)`

Opening balances have no expiry (INV-15).

Two small additions made while writing 005:
- **`stock_movements_not_own_reversal`:** a line cannot reverse itself.
- **A required reason cannot be only spaces** (`btrim(reason) <> ''`). `btrim` strips spaces only, so the services
  must trim the reason with JavaScript `trim()` first and answer a blank one with a 400. That way a reason of
  spaces, tabs or other blank characters is a plain message, never a server error.

**Rules a CHECK cannot express.** Each is enforced by the server under the ingredient lock and has its own test:
- A reversal's quantity is exactly minus the purchase's quantity. The reversed line is a `purchase` or an
  `opening` (Q51). Its `effective_date` is the purchase's own date.
- A `void_return` is exactly minus its `run_use`.
- Pieces are whole numbers, a multiple of 1000 (Q53). A CHECK cannot see `base_unit`.
- The run on a `run_use` line has its cost line for this ingredient. 006 makes this a foreign key (3.2).
- A `run_use` line's quantity and unit cost equal its `run_costs` line.

The stock check (2.4) verifies each of these rules again over the whole ledger.

**Unit-price CHECK.** On `opening` and `purchase` lines: `total_cost_cents <= 100000 * quantity_milli`. That is
the P1,000,000-per-unit limit written so it fits in bigint. The server tests the same integer inequality
before inserting, never a rounded unit price, so a value just over the limit gets a 400, not a 500.

### 1.5 `purchase_detail_changes`: audit trail for INV-17 (append-only)

| Column | Notes |
|---|---|
| movement_id | FK (tenant_id, movement_id) to stock_movements; indexed |
| supplier, reference, expiry_date | the values **before** the change. Supplier and reference are NOT NULL, at most 120 characters, like the ledger |
| changed_by_user_id, changed_by_name, changed_at | 1.0 |

The change runs in one transaction: lock the ingredient, insert the "before" row, then update the three
columns. Owner only. Grants: SELECT and INSERT.

The server refuses a correction:
- on any line that is not a purchase;
- on a purchase that has been reversed;
- that changes nothing ("nothing to change"). This way no empty audit rows are ever written.

## 2. Numbers and the stock maths (P4-05)

### 2.1 Units, limits and precision

**Units:**
- **Quantity:** an integer number of **thousandths of the base unit** (`_milli`), which gives the 3 decimals
  INV-04 asks for.
- **kg and L (Q42):** the typed decimal text is converted by integer arithmetic on its digits, never by
  floating-point multiplication. So 1.25 kg becomes 1,250,000 milli-g exactly.
- **Input with too many decimals is refused,** not rounded: at most 6 decimals for kg and L, 3 for g and mL,
  and none for pieces (Q53).
- **Average:** an integer number of **ten-thousandths of a centavo per base unit** (`_e4`).
- **Money:** whole centavos (`_cents`), as everywhere else.

**Limits,** each checked by the server with a 400 and backed by a database CHECK:
- A quantity per entry is at most 10,000,000 base units (10^10 milli).
- A purchase total is at most P20,000,000 (2,000,000,000 centavos, the app's existing money limit).
- A **unit price is at most P1,000,000 per base unit** (10^12 e4). This stops a tiny quantity with a huge
  total from making an average no computer integer can hold. Because the average is a weighted mix of unit
  prices, it can never pass that limit either.
- An ingredient line's amount is at most 2,000,000,000 centavos, and a run's total at most 2,147,483,647
  (the `integer` column limit). Anything larger is refused with a plain 400.

  The run total check also fixes a gap that exists today: 100 lines at the limit can overflow the run total.
  It is tracked separately as P2-16.

**Calculation:**
- **Reading `bigint` values back.** node-postgres returns `bigint` as a string. PGlite returns a number when
  the value is safe and a `BigInt` otherwise, and `SUM(bigint)` returns `numeric` on both. One helper turns
  string, number or BigInt into a JavaScript integer and fails outside the safe range. It is tested on both
  databases.
- All multiplications and divisions use `BigInt`.
- Rounding is half up.

### 2.2 One step function, used everywhere

`applyEntry(state, entry) -> state`, where `state = { onHandMilli, avgE4 | null }`. It lives in `calc/stock.ts`
and is the only code that changes these values.
- Purchase or opening balance, when `onHandMilli > 0` and `avgE4` is set:
  `avgE4 = roundHalfUp((onHandMilli × avgE4 + totalCents × 10^7) / (onHandMilli + qtyMilli))`
- Purchase or opening balance, when `onHandMilli <= 0` (Q33), **or when there is no average yet** (Q49):
  `avgE4 = roundHalfUp(totalCents × 10^7 / qtyMilli)`
- Every other kind changes `onHandMilli` only.
- The average is rounded to e4 **after every step**. The fast path and the replay call this same function,
  so they give the same answer to the last digit.
- Line cost (BR-20): `amountCents = roundHalfUp(qtyMilli × avgE4 / 10^7)`.
- Worked example: 496 mL at P0.10/mL, plus 500 mL bought for P60, gives 110,040 e4, which is **P0.11004/mL**.
  2 mL at P0.10/mL costs 20 centavos.

  BRD v0.8 INV-04 says "about P0.1104", which is a typo. BRD v0.9 corrects it so QA tests the right number.

### 2.3 Date order, the fast path and the replay (Q38, Q45)

- **Replay:** fold `applyEntry` over the ingredient's ledger in date order (`effective_date`, then `id`). A
  reversed line and its reversal are both left out.
- **Fast path:** if, after taking the lock, the new line's `effective_date` is on or after the latest
  `effective_date` in that ingredient's ledger, apply the one step to the cached copy. In every other case
  (any back-dated line, and **every reversal**), replay the whole ledger and store the result.
- **Saved runs keep the cost they used** (Q45). The replay never touches `run_costs` or `unit_cost_e4`.
- **On hand** is the plain sum of the ledger, so the order does not affect it.

### 2.4 The stock check (drift guard)

`npm run stock-check` (`server/src/scripts/stockCheck.ts`) connects like backup and restore do, as the
database owner from the command line. For every business and ingredient, it replays the ledger and compares
the result with the cached copy.
- It prints every difference and exits with code 1 if there are any.
- **No false alarms while the app runs:** it reads each ingredient's copy and ledger under `FOR SHARE` on the
  ingredient row, so a save landing in between cannot look like drift.
- **What it also checks:** the rules only the server enforces (1.4), and that each ingredient has at most
  one standing opening balance (Q51).
- **`--fix`** locks each ingredient (`FOR NO KEY UPDATE`) while it replays and writes, so it is safe against a
  running server. It writes the replayed values back, adds 1 to `avg_version` whenever it changes an average,
  and prints what it changed. It never changes ledger lines.
- **After every `npm run restore`** it runs automatically. The restore has already been committed by then, so
  the check only reports; it cannot undo the restore.
- **The tests** call the same function after every stock test (P4-19).

### 2.5 Blocks and warnings (INV-06, BR-21, Q37, Q44)

- **Checked at Save, under the lock.** The preview runs the same checks without locks, for display only.
- **Lines of one ingredient are added together first** (Q44).
- **Blocked:** an ingredient with no standing opening balance or purchase (one that is not reversed), or one
  whose on hand is already below zero. This applies even to a 0 line, and no one can override it.
- **Warned but allowed:** a run that takes on hand below zero.
- **Archived ingredients (Q50):** they cannot be bought or used in new runs, but voids and owner
  corrections still work on them.

### 2.6 Corrections and reversals

- **Count correction (Q52).** The owner types the counted quantity and a date. Under the lock, the
  server works out the difference: the count minus the sum of all ledger lines dated on or before that date
  (counted at the end of that day). It stores only the difference. Later-dated lines are unaffected. If the
  count equals the computed on hand, the server says "nothing to correct" (400) and stores nothing.
- **Purchase reversal (INV-16).** It is allowed only while the purchase is the last entry made for the
  ingredient, whatever its date (D-45, as for openings in D-42): otherwise a mistyped price on a back-dated
  purchase could never be taken out of the average. Lines already undone do not count (D-43). The reversal is
  dated the purchase's own date, and it always replays.
- **Opening balance.** Allowed once (Q46). A wrong one can be reversed, then entered again (Q51). For an opening
  the last line means the last entry made, whatever its date (D-42): it is often dated before a purchase already
  recorded. The one-standing-opening rule in 1.3 applies.
- **Future dates (Q54).** Purchases, opening balances and corrections may not be dated after today
  in the business's time zone. Runs keep today's behaviour, and the fast-path rule in 2.3 already copes with
  future-dated runs.

## 3. Runs that use stock (database change 006, part 4b)

### 3.1 New columns on `run_costs` (null on every existing row)

| Column | Notes |
|---|---|
| ingredient_id | FK (tenant_id, ingredient_id) to ingredients |
| ingredient_name, base_unit | a snapshot, as `run_products.product_name` is, so renaming an ingredient never changes an old run's detail (INV-11) |
| quantity_milli | bigint CHECK 0 to 10^10 |
| unit_cost_e4 | bigint CHECK 0 to 10^12 |

- **CHECK:** either all five are null, or all are set and `category = 'ingredient'`.
- **The costing engine (`calc/engine.ts`) is unchanged.** `amount_cents` stays the line's amount, and the
  engine still receives peso cost lines.
- **Old peso "ingredient" lines** keep `ingredient_id` null and still display.
- **When a run uses stock.** A run gets stock lines only when inventory is live and the run is dated on or
  after `inventory_live_since`. Otherwise it is saved exactly as today.
- **Saved run details become unchangeable.** 006 revokes UPDATE on `run_products`, `run_packings`, `run_costs`
  and `run_cost_targets` from the app role. Today's code never updates them, and a test proves the app role
  cannot. A saved run's amounts, unit costs and quantities then cannot be rewritten (BR-20, RUN-06). The
  `runs` row itself keeps UPDATE, because voiding uses it.

### 3.2 Linking the ledger to the run line

006 adds `UNIQUE (tenant_id, id, ingredient_id)` on run_costs and a foreign key from the ledger:
`(tenant_id, run_cost_id, ingredient_id)` to `run_costs (tenant_id, id, ingredient_id)`. A run's stock line
can then only point at that run's line for the **same ingredient**.

The ledger columns themselves (run_id, run_cost_id, unit_cost_e4) are created in 005 (1.3).

## 4. Locking: two people at once (P4-11, P4-19, D-24)

Transactions stay at PostgreSQL's default level, read committed, with explicit row locks, as the price
history does (P2-06b). These are the rules:

0. **The `business_settings` row is locked before any ingredient, never after.** Run Save takes `FOR SHARE`;
   only setting the live date takes `FOR UPDATE` (1.1).
1. **Lock first, then read.** Every stock change starts with
   `SELECT ... FROM ingredients WHERE id = ANY($1) ORDER BY id FOR NO KEY UPDATE`, in ascending id order so two
   saves cannot deadlock. The server checks the lock returned every id it asked for. On hand, the average
   and the ledger are read only after the lock.
2. **Never lock an existing `runs` row after locking ingredient rows.** The order is always: the run first
   (void only), then the ingredients.
3. **Purchase, opening, correction, reversal, detail correction:** lock the ingredient, check the rules,
   insert the line, then fast path or replay (2.3), and commit.
4. **Saving a run:** lock every ingredient on the run, re-price each line from the locked average, check the
   blocks (2.5), and compare the prices with the ones the person reviewed (below).
   - If they differ, refuse with **409, "Ingredient prices changed since you reviewed this run. Review it
     again."** (Q36).
   - Otherwise insert the run, its cost lines with ingredient details, and one `run_use` per ingredient line,
     then update the cached copies.

   **How "the prices the person reviewed" is checked without showing costs to staff:**
   - The preview returns `ingredientVersions`: `{ ingredientId: avg_version }` for each ingredient on the run.
   - The browser sends it back unchanged with Save.
   - The server compares it with the locked `avg_version` values.

   The quantities are the person's own input, so the total can only change if an average changed. The
   versions are plain counters, so they reveal no cost. The edge cases:
   - **Slightly stricter than Q36.** It also asks for a new review when an average moved too little to change
     any rounded amount. That costs one extra click, at worst, and needs no new server secret.
   - **The ingredients must match.** Save is refused if the versions sent do not cover exactly the ingredients
     on the run.
   - **One read.** The preview reads each version in the same SELECT as its average.
   - **Warnings the person did not see.** The preview also returns `belowZeroWarnings`: the ingredients it
     warned would go below zero (quantities, not costs, so staff may see them). If another save makes a new
     ingredient go below zero after the review, Save is refused with its own message: "Stock changed since you
     reviewed this run: some ingredients would now go below zero. Review it again." Nobody saves past a
     warning they were never shown. This is a new refusal; INV-06 and Q36 do not ask for it, so it is listed
     for Al in "In short".
5. **Voiding a run** becomes one transaction (today it is a single query):
   - The existing guarded `UPDATE runs ... WHERE status = 'saved' RETURNING id` runs first. If no row comes
     back, it stops with 404 or 409, as now.
   - Then it locks the run's ingredients, inserts one `void_return` per `run_use`, and updates the copies.
     The return is dated the void date in the business's time zone (`localToday()`), not the UTC date of
     `voided_at`.

   The unique index on `(run_cost_id) WHERE kind = 'void_return'` backs this up in the database.
6. **The preview takes no locks.** It is also allowed while a subscription has lapsed, so it must not block
   saves.

The built-in database (PGlite) has one connection, so these waits only happen on PostgreSQL. The tests that
prove them (P4-11, P4-19) run against the PostgreSQL 16 on this PC, in a separate test database. They also
prove how PostgreSQL itself behaves: which locks foreign keys take, that the lock query locks rows in order,
and when foreign-key checks fire.

## 5. Expiry board (4d: INV-12, INV-15, BR-27): nothing extra stored

The board is worked out when it is read, by replaying the ledger in date order over a list of stock lots:

| Line | Effect on the lots |
|---|---|
| purchase | adds a lot with its expiry date (or no expiry) |
| opening balance, positive count correction | adds a lot with **no expiry** |
| run use, spillage, spoilage, negative count correction | takes from the lot that expires soonest. Expired lots are the soonest, so they go first. No-expiry lots go last |
| void return | gives back to the same lots its run use took from, in this same replay (Q41) |
| purchase and its reversal | both left out of the lot replay entirely, as in the average replay. Even if owed stock had been paid from that lot, it never happened |

Stock taken while nothing is left is owed, and is taken from the next lots that arrive. So whenever on hand is
zero or more, the lots add up to on hand. Two edge cases, defined here for P4-29:
- **A void return of a run use that was partly owed.** The part that came from lots goes back to those lots.
  The owed part cancels that much of the debt; if the debt was already paid from a later lot, it goes back to
  that lot.
- **A void return dated before its run use** (a future-dated run, section 10). The returned quantity is held
  and applied to the lots at the run use's own date in the replay, so it never creates stock before the run
  took it.

Because nothing is stored, back-dating and corrections never leave the board out of date. This replaces the
earlier plan to store "which purchases each run used" in change 006. The Project Manager has updated P4-15
and P4-29 to match. It saves work and does not change what the owner sees.

## 6. Who sees what, and cutover

**Staff (INV-14, USR-12):**
- **Ingredient costs are hidden from staff from part 4a onwards, always.** That means averages, purchase
  totals, unit prices and the ingredient price history (INV-14, P4-12, P4-13).
- **Run costs are hidden from staff once inventory is live,** using the Q48 list: run review, run detail,
  History total, CSV cost columns, the Margins page, packaging cost and the product price history (USR-12,
  P4-36).
- Owner-only actions are refused with 403 through the existing `kit.requireOwner`.
- Staff see ingredient names, units, quantities on hand and expiry dates. They never see unit costs,
  averages, purchase totals, or either price history.

**Business export (D-33).** "Download my data" (`GET /api/export`) has no owner check today, so a staff
member could download every cost. **Decided (D-33): owner-only, built now as P2-17.**

**How inventory starts (D-34, revised after review round 2).** Draft 2 proposed a "shadow period": opening
balances first, then real purchases for a few weeks while runs do not use stock yet.

**The Code Reviewer showed that this makes the averages wrong.** The shadow-period runs use stock the ledger
never hears about, so every purchase is averaged against stock that is already gone. For example:
- Opening balance: 1,000 g at P1/g.
- Shadow-period runs use 900 g, which is not recorded.
- A purchase adds 1,000 g for P2,000.
- The ledger says 2,000 g at P1.50/g. The truth is 1,100 g at about P1.91/g.
- The cutover count removes the 900 g but leaves the average at P1.50/g.
- Runs would then be costed about 21% too low until that stock is used up.

**Options for D-34:**
- **(a) No shadow period. Chosen by Al (D-34).** On cutover day, after 4b passes QA, the owner enters an opening
  balance for every ingredient and sets inventory live the same day. That is the original D-26. You can
  still practise purchases, corrections and runs beforehand on the trial business on Render, with fake data.
- **(b) Shadow period with a count before every purchase.** Just before each shadow-period purchase, the
  owner records a count correction, which Q52 makes easy. This is correct, but it is a chore and easy to
  forget. The count must come first in date order: the same date as the purchase, entered before it. A
  purchase entered late with an earlier date therefore needs its own count, dated that same day and entered
  before the purchase.
- **(c) Shadow-period runs record stock use only,** while their costs stay as peso lines. This is correct,
  but it needs part 4b first and changes 4b and database change 006.
- **(d) Accept the error.** It fades only slowly, depending on how much old stock is left at each purchase.
  In the example, the next 1,000 g bought at P2/g gives P1.74/g in the app against P1.95/g in reality: still
  about 11% low.

**Whichever option is chosen, from `inventory_live_since` (set once, to that day):**
- New runs dated on or after it take their ingredients from stock.
- The peso "ingredient" line is refused on those runs (Q35).
- Staff stop seeing run costs.

Runs dated before that day are entered the old way. Database change 005 is the same for (a), (b) and (d);
only (c) changes 006.

## 8. Backup, restore and the table lists

- `TENANT_TABLES` (fill order, parents first): `products, pack_sizes, pack_size_changes, business_settings,
  ingredients, runs, run_products, run_packings, run_costs, run_cost_targets, stock_movements,
  purchase_detail_changes`, then the 007 tables.
- **Restore works with the ledger's self-reference.** Restore inserts each table in one
  `INSERT ... SELECT FROM json_populate_recordset` statement. Non-deferrable foreign keys are checked at the
  end of that statement, so a reversal and its purchase can be in any order inside it.
- **Backup and restore code stay unchanged,** because every new table has an `id`. The restore test is
  extended with a `business_settings` row, a purchase, a reversal, a run that uses stock and a void, and it
  checks the stock check reports no difference after restoring.
- The start-up isolation check (`assertIsolation`) covers the new tables through `TENANT_TABLES`: row-level
  security must be on, and a business that does not exist must see no rows in any of them.
- **The unique indexes on the ledger are global, not per business.** So a hand-written insert pointing at another
  business's line can get a "reversed once" error instead of a foreign-key error, which tells it the line exists.
  The services must always look up the target through the scoped handle and answer 404 before inserting.

## 9. Cross-business and permission tests, per table (in `tenancy.test.ts`)

| Table | Tests |
|---|---|
| business_settings | another business cannot read or write it. Hand-written SQL as business B cannot insert a row for A |
| ingredients | not visible across businesses; no insert for another business; the unique name is per business |
| stock_movements | not visible across businesses. Even the table owner cannot link a line to another business's ingredient, run, run line or reversed line (composite FKs). The app role cannot DELETE, and cannot UPDATE quantity, cost, date, kind, links or `tenant_id` (column grant). A reversal cannot point at another ingredient's line |
| purchase_detail_changes | not visible across businesses; the app role cannot UPDATE or DELETE. Even the table owner cannot link a row to another business's ledger line |
| run_costs (006) | the new unique keys and the ingredient FK refuse a link to another business's ingredient or run. The app role can no longer UPDATE run_products, run_packings, run_costs or run_cost_targets |

Each table gets one test that bypasses the app's code and sends hand-written SQL as another business, to prove
row-level security alone blocks reading, adding and linking across businesses. `tenancy.test.ts` already does
this for the price history.

## 10. What the owner should know (for the screens and the user notes)

- **A past average can change.** A back-dated entry changes the "average after each purchase" shown in the
  ingredient price history (INV-10), because it is worked out again in date order. Saved runs never change.
- **A void return can come before its run.** A void return is dated the day of the void. If a run was dated
  in the future and then voided before that date, its stock comes back before it was used, in date order.
  This only shifts the averages of purchases in between.

## 11. Review points for the Code Reviewer and Al

1. **Column-level UPDATE on the ledger** for supplier, reference and expiry only, with the old values kept in
   `purchase_detail_changes` and the CHECKs in 1.4. A separate details table would give the same protection
   with an extra join everywhere.
2. **Cached on hand and average on `ingredients`**, with the stock check (2.4) as the guard against drift.
3. **Void returns are dated the void date,** not the run date.
4. **No back-dating limit** (Q45) means one old entry replays a long ledger. That takes milliseconds at this
   business's size. If it ever gets slow, a yearly checkpoint can be added without changing the tables.
